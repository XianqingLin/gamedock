# GameDock：业务评审记录

本文记录原始 `PROJECT_PROMPT.md` 中业务描述的歧义、冗余和表达优化，以及后续入店流程修订。当前执行规则以[产品需求](./01-product-requirements.md)为准，场景空间与生成约束以[3D 场景描述](./04-scene-description.md)为准。文中明确标记为“已替代”的旧决策不再执行；如需变更，应同步修改产品需求、场景描述及对应验收项。

## 1. 歧义与统一结果

### 1.1 声音是否为当前版本必做

- 原描述：首页要求提供声音开关，后文又写“声音不是首版核心功能”“如实现声音”。
- 问题：无法判断声音及开关是否属于验收必需项。
- 统一结果：声音为当前版本可选功能；只有实现声音时才显示开关，且不得阻塞核心流程。

### 1.2 首页是否默认选中游戏

- 原描述：首页要求默认展示店铺总览，同时包含“当前选中游戏的详情面板”，未说明初始选中项。
- 问题：实现可能自动选中第一款游戏，形成变相推荐，也可能出现空详情面板。
- 统一结果：首次进入不自动选中游戏、不打开游戏详情，未选择时隐藏详情和启动按钮。店铺总览已不再作为固定出生机位，入店位置按第 4 节的新规则处理。

### 1.3 筛选排除当前选中游戏后的行为

- 原描述：“清除选中状态或选中首个可见结果，行为保持一致。”
- 问题：两个选项会导致不同的详情、URL 和浏览路径，不能算确定需求。
- 统一结果：清除选中状态并关闭详情，不自动选中首个结果，避免用户在浏览筛选结果时被动跳转。

### 1.4 搜索范围与匹配规则

- 原描述：搜索匹配游戏名称，“可扩展匹配分类”，未说明大小写、空白或匹配方式。
- 问题：“可扩展”使首版范围和测试预期不固定。
- 统一结果：当前仅匹配名称；忽略关键词首尾空白和英文字母大小写，采用包含匹配，不做拼音或模糊搜索。搜索与分类按“同时满足”组合。

### 1.5 关闭详情、浏览器返回和 Escape 的关系

- 原描述：“关闭按钮、浏览器返回和 Escape 行为保持一致”，但直接打开详情 URL 时没有可返回的站内历史。
- 问题：若要求完全相同，会与浏览器历史语义冲突。
- 统一结果：关闭按钮和 `Escape` 行为一致，退出详情并保留浏览条件；浏览器前进、后退遵循实际访问历史，不再要求三者产生完全相同的结果。

### 1.6 “可用”但无有效启动地址

- 原描述：可用游戏显示“开始游戏”，同时又要求缺少启动地址的游戏不能进入空白页面。
- 问题：数据状态与启动能力冲突时，按钮文案与可用性不明确。
- 统一结果：启动能力由状态与有效地址共同决定。“可用”但地址缺失或无效时显示“暂不可启动”并禁用启动按钮，与“未开放”“维护中”区分。

### 1.7 小屏、减少动态效果与低性能设备的默认模式

- 原统一结果：视口小于 768px 时首次进入默认列表，其他情况默认场景；WebGL 或关键 3D 资源失败时自动降级列表；减少动态效果只关闭非必要动画。
- 本轮修订：**小屏默认规则已替代**。当前版本只验收桌面端，不再以 768px 决定默认模式；手机端和低性能设备的独立 2D 网站属于后续范围。桌面列表模式继续保留，用于辅助浏览和 3D 故障降级。
- 仍然有效：WebGL 不可用、3D 初始化或关键场景资源失败时自动使用桌面列表；减少动态效果只简化非必要动画和门状态反馈，不强制切换列表。

### 1.8 同等视觉权重与选中反馈

- 原描述：所有游戏保持同等视觉权重，同时允许选中抽盒、高亮和镜头移动。
- 问题：可能被误解为选中时也不能突出显示。
- 统一结果：平等指默认陈列规格、信息层级、排序权重和交互规则一致；悬停、聚焦、选中产生的临时反馈不属于特殊推荐。自主移动模式下不强制通过镜头运动表达选中。

### 1.9 演示数据与正式游戏数据的边界

- 原描述：允许演示游戏验证布局，但不得伪装成已正式接入的游戏，未说明使用环境。
- 问题：演示数据可能被误用为正式内容。
- 统一结果：演示数据仅用于开发、测试或明确的演示环境，不作为正式接入内容发布。正式上线数据不足时宁可显示空数据状态，也不编造游戏。

### 1.10 不同资源失败时的降级范围

- 原描述：分别提到 WebGL、3D 资源、封面和音频失败，但部分条目只写“保留能力”。
- 问题：无法判断各类故障下哪些功能仍必须可用。
- 统一结果：WebGL、3D 初始化或关键场景资源失败时自动使用桌面列表；单个封面失败使用默认封面；音频失败只停用声音；单个非关键装饰失败不影响应用。新增注册流程后，3D 失败也不得阻断必要的注册操作。

### 1.11 默认陈列顺序

- 原描述：游戏具有排序字段，又要求所有游戏权重一致，未说明排序如何生效。
- 问题：可能把排序误解为推荐或热度权重。
- 统一结果：默认按统一数据顺序稳定陈列，不引入推荐或热度权重；技术层规定排序值相同时按稳定标识排序，避免渲染顺序漂移。

### 1.12 声音偏好保存与禁止自动播放

- 原描述：声音只能由用户主动开启，同时要求保存用户选择。
- 问题：恢复“已开启”偏好时，可能被实现为刷新后自动播放。
- 统一结果：可以保存偏好，但页面重新打开后仍需遵守用户手势和浏览器自动播放限制，不得直接播放。

## 2. 冗余描述的合并

- 共享数据与模式同步：由产品需求第 4 节统一描述用户行为，技术要求第 3、4 节统一描述数据与状态实现。
- 启动限制：由产品需求第 4.4 节集中定义状态，技术要求第 2 节定义协议校验和跳转。
- 游戏平等：由产品需求第 2.1 节统一规定，并保留结果导向的验收项。
- 入店与接待：产品需求第 3 节规定不同用户的业务顺序，场景描述第 3 至 7 节规定对应的空间锚点、门、前台和移动关系，技术文档规定状态实现，避免三处分别定义不同出生点。
- WebGL 与资源降级：由产品需求第 8 节定义用户结果，技术要求第 7 节定义故障隔离。
- 动画与减少动态效果：由产品需求第 5.4 节统一描述，场景描述补充店门动画的空间和碰撞约束，技术文档说明实现覆盖范围。
- 文案限制：由产品需求第 2.2 节集中规定；服务员问候属于接待文案，不因此开放营销口号。
- 验收标准：不再完整复述所有需求，只保留能直接验证的结果，详细规则通过章节引用追溯。

## 3. 表达与可验收性优化

- 区分“必须”“可选”和“后续接入”，减少“可默认”“即可”或不产生确定验收结果的措辞。
- 为原先“短促”“足够大”“足够对比度”等主观描述设置默认值：常规交互动画不超过 300ms，DOM 点击目标至少 44×44 CSS 像素，普通文字对比度至少 4.5:1，并增加 200% 页面缩放检查。店门动画作为功能性场景动画，不套用 300ms 上限。
- 将“游戏数据为空”与“搜索无结果”拆成不同状态，避免空数据时错误地提供“清除筛选”作为解决手段。
- 书脊允许在空间不足时截断文字，但详情与无障碍名称必须保留完整游戏名。
- 业务文档保留“可分享 URL”等产品能力，具体路由、协议、状态字段和组件要求移至技术文档。
- 将用户状态、初始位置和门状态写成可分别验收的规则，避免用“进入店铺”同时指代镜头动画、角色移动和场景加载。
- 技术验收要求报告实际执行的测试；未执行的浏览器验证必须明确说明，避免把“建议检查”写成“已经通过”。

## 4. 自主移动与入店流程修订

### 4.1 注册与服务员进入当前范围

- 新描述：前台设置服务员；新用户首先注册，已注册用户由服务员打招呼。
- 替代关系：原“用户注册、登录不属于首版范围”的决策不再适用于新用户注册和已注册用户识别。注册所需的最小身份能力进入当前范围，但支付、社区等账号扩展功能不随之加入。
- 尚未确定：创意注册的具体形式、注册字段、登录方式、会话与身份服务不得自行编造，见第 5 节。

### 4.2 新用户与已注册用户采用不同出生点

- 新用户：位于店门外并朝向入口，自主开门、进店并走到前台。
- 已注册用户：位于前台稍前方并面向服务员，不重复店外流程。
- 判定原则：出生点由可验证的注册状态决定，不由是否播放过动画、是否看过门店或单个本地标记代替。
- 注册成功后：用户保留当前店内位置并恢复自主移动，不通过刷新将其重新放回门外。

### 4.3 店门动画与镜头动画分开定义

- 店门不再默认敞开，必须提供打开与关闭动画，并与实际通行和碰撞状态一致。
- 原“新用户从店外通过镜头移动进入店内”的方案取消；用户自主移动入店，不自动把镜头推到前台。
- 已注册用户直接在柜台前接待，不需要播放门动画或入店镜头。
- “不需要动画”按上下文理解为不需要强制入店和接待镜头动画，并不取消用户明确要求的门开关动画，也不取消必要的游戏盒反馈。

### 4.4 自主移动替代固定机位主导航

- 原“总览、货架、详情三个稳定机位，不要求 WASD 行走”的规则已替代。
- 当前桌面版以自主移动作为店内主导航，场景需要提供可行走区域、碰撞、边界和卡住恢复。
- 不再把“返回总览”作为固定机位验收项，但仍需保证用户能够恢复位置、退出画布输入并使用全部页面控件。
- 具体视角方案、移动按键和指针锁定细节属于待确认的实现决策，不能据此宣称同时支持第一人称、第三人称或所有控制方式。

### 4.5 桌面版、桌面列表与未来 2D 网站的边界

- 当前版本不考虑手机端适配，删除小屏默认列表、触摸移动、移动端渲染质量和移动端布局验收。
- 当前桌面列表模式保留，继续提供完整浏览能力并承担 3D 故障降级。
- 面向手机端和低性能设备的常规 2D 网站是后续独立交付，不以当前桌面列表简单缩放代替，也不纳入当前版本完成声明。
- 桌面 200% 缩放、键盘和减少动态效果仍属于当前可访问性要求。

### 4.6 场景描述独立维护

- 新增[3D 场景描述](./04-scene-description.md)，集中说明空间布局、锚点、门面、大门、前台、服务员、货架、移动边界和 AI 生成资源约束。
- 产品需求决定“哪类用户执行什么流程”，场景描述决定“流程在空间中的位置和关系”，技术实现要求决定“如何实现与验证”。
- AI 生成只改变资产与场景的生产方式，不降低版权、资源本地化、统一陈列、碰撞、性能和可访问性要求。

### 4.7 从游戏店调整为科技收藏馆式据点

- 场景定位由单纯游戏店调整为玩家据点：据点承担接待、游戏选择和长期成长展示，具体游戏与联机仍在独立游戏页面进行。
- 当前布局确定为门后环形前台，环形前台左侧后方为游戏陈列区，右侧后方为成就展区，中央设置原创“存档核心”雕塑。
- 环形前台当前只启用门口侧服务员，其余服务位仅预留空间和锚点，不以无职责人物或假交互提前填充。
- 联机房间和匹配不进入 3D 场景，且平台不提供（各游戏联机自理）；好友邀请是平台层能力（好友列表/通知，仅传递邀请信息）；游戏介绍等当前游戏相关功能由独立游戏页面的固定外边框承载。
- 成就展区现在只确定空间和美术结构，成就系统仍在当前功能范围之外。未接入时不得展示虚构徽章、进度或排行榜。
- 视觉方向由纯复古游戏店调整为“温暖科技风＋收藏馆式陈列”，保留深色木材与暖光，加入哑光金属、有序环形结构和少量青蓝点缀，不采用满墙蓝紫霓虹的赛博方向。
- 场景描述中的尺寸、左侧铰链门、柜台分段和雕塑结构属于本轮补齐的默认设计，可在灰盒验证后调整，不视为新增账号、成就或联机业务规则。

## 5. 尚待真实项目补充的信息

以下内容当前没有足够依据，不得擅自编造：

- 创意注册的最终形式、注册字段、登录方式、账号数据、会话与身份服务，以及注册失败和重复注册的服务端规则。
- “新用户”和“已注册用户”的正式身份判定来源；在方案确定前，不得把单个本地标记描述为正式账号体系。
- 第一人称或第三人称视角、具体移动按键、鼠标灵敏度、是否使用指针锁定及其页面级替代操作。
- 灰盒验证后的最终尺寸、服务员具体形象与实际数量、门动画时长、最终场景资产格式及生成工具。
- 成就的数据来源、解锁规则、展示内容和交互方式，以及独立游戏页面外边框与好友邀请的具体实现。
- 正式游戏清单、分类、封面、介绍、版本和启动地址。
- 在线人数的真实数据源与更新频率；没有来源时继续隐藏。
- `updatedAt` 指游戏内容更新时间还是平台数据更新时间；接入真实数据前需统一含义，未明确前不应展示。
- 正式桌面浏览器与设备支持矩阵。当前只明确桌面端和核心可访问性行为，不能据此宣称支持所有浏览器或手机端。
- 首屏时间、帧率、内存和资源体积等量化性能预算。需要在目标桌面设备、网络条件和真实资源规模明确后补充；当前性能要求只能作为实现约束，不能替代量化性能验收。
