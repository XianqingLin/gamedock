# 小林游戏铺：技术实现要求

本文规定工程、数据、渲染、移动、性能、安全和测试要求。用户可见行为与默认规则以[产品需求](./01-product-requirements.md)为准，空间布局、逻辑锚点和 AI 场景资源以[3D 场景描述](./04-scene-description.md)为准，本文不重复定义相冲突的业务规则。

## 1. 交付方式与技术栈

直接在当前工作目录交付可运行的实际代码、本地资源和必要配置，而不是示例、设计稿或代码片段。若已有工程，先检查并沿用现有技术栈与结构；目录为空时采用：

- Vite
- React
- TypeScript
- React Router
- Three.js
- `@react-three/fiber`
- `@react-three/drei`
- CSS Modules 或结构清晰的普通 CSS
- Vitest 与 React Testing Library

当前工程只交付桌面端 3D 应用及桌面列表模式，不加入手机虚拟摇杆、触摸移动或小屏适配分支。面向手机端和低性能设备的独立 2D 网站是后续交付，不在当前工程中用未验收的响应式页面冒充完成。

不为了简单功能提前搭建无关后端，不引入只解决假想需求的大型依赖，也不增加无实际作用的抽象层、通用框架或复杂事件总线。注册与身份识别已经进入当前业务范围，其所需接口应按真实方案实现，不能以“无后端”为由伪造正式注册能力。

## 2. 路由与启动实现

- `/`：首页，承载场景或列表浏览，以及对应的接待与注册界面。
- `/games/:slug`：游戏详情，可实现为独立页面或支持路由的面板；必须支持直接访问、刷新恢复、浏览器前进和后退。
- `/play/:slug`：按实际接入方式进入同域游戏或执行受控跳转。
- 其他路由：显示路由未找到状态和返回首页入口。

关闭详情与筛选导致选中失效时，应同步清理对应详情路由，避免 URL 继续指向已取消选择的游戏。搜索、分类和模式状态可通过共享状态或 URL 协调，但必须满足产品规定的模式切换与关闭详情行为。

启动处理要求：

- 同域游戏通过站内路由加载。
- 外链只接受 `http:` 和 `https:` 协议；解析后协议不符合要求时按无效地址处理。
- 使用新窗口打开外链时设置 `noopener`、`noreferrer` 等安全属性。
- 游戏不存在、未开放、维护中或启动地址缺失、无效时，不创建空白路由或空白窗口。
- 启动失败不能破坏当前浏览状态。

路由切换、详情打开或场景与列表切换不得无故重新执行出生点初始化。需要恢复用户位置时，应区分详情导航、页面刷新和真实重新进入，不得把所有路由变化都视为新用户入店。

## 3. 游戏数据

游戏陈列、列表和详情必须使用同一份数据。可使用 TypeScript 数据文件或 JSON，参考结构如下，可按实际需要最小调整：

```ts
type GameStatus = 'available' | 'coming-soon' | 'maintenance'

interface Game {
  id: string
  slug: string
  title: string
  cover: string
  accentColor: string
  categories: string[]
  description?: string
  launchUrl?: string
  status: GameStatus
  onlineCount?: number
  version?: string
  updatedAt?: string
  order: number
}
```

数据约束：

- `id` 和 `slug` 必须唯一且稳定，不以数组下标充当持久标识。
- 分类独立维护并通过稳定标识关联，避免在多个组件中重复硬编码分类名称。
- 默认按 `order` 升序排列；`order` 相同时按 `id` 排序，保证结果稳定。
- `description`、`onlineCount`、`version`、`updatedAt` 等可选字段没有有效数据时保持缺省，不渲染空标签。
- `onlineCount` 只能来自真实数据，不使用随机数或静态数字模拟实时人数。
- 第一款游戏与其他数据使用相同结构和组件。
- 演示数据只能用于开发、测试或明确的演示环境，不得伪装为正式接入内容。
- 新增游戏只需新增数据及必要资源，不修改场景组件。
- 封面路径无效或资源加载失败时统一回退到本地默认封面，不使用随机外链占位图。

## 4. 用户、组件与状态管理

### 4.1 用户身份与注册状态

- 至少区分身份加载、新用户、已注册用户和身份错误状态，不能在身份尚未确认时默认按已注册用户处理。
- 新用户与已注册用户必须由可验证的注册状态区分。正式环境不能只凭 `localStorage` 中的布尔值、是否看过动画或是否完成过对话认定注册成功。
- 注册字段、登录方式、会话和服务端接口尚未确定，应通过清晰的边界隔离身份查询与注册请求，避免把临时演示实现散落在场景组件中。
- 演示身份或模拟注册只能用于开发、测试或明确标识的演示环境，不得作为正式账号能力交付。
- 注册成功后统一更新身份状态，保留当前用户位置和浏览状态，不通过页面刷新完成状态迁移。
- 注册与身份请求需要处理加载、失败、重复提交和恢复；错误不得被场景动画或问候文案掩盖。
- 密码等敏感凭据不得写入本地存储、日志或游戏数据。具体认证安全要求随正式身份方案补充，但不得传输或保存明文密码作为演示以外的实现。

### 4.2 组件与状态拆分

- 按职责拆分场景、入口与店门、移动控制、碰撞、前台与服务员、注册对话、货架、游戏盒、详情、搜索筛选和列表视图，避免为每款游戏复制场景代码。
- 样式、场景配置、锚点、分类数据、游戏数据和身份接口分离。
- 出生点选择由身份状态统一派生，店门、服务员和移动控制器不得各自判断一套互相冲突的用户类型。
- 出生点只在真实初始进入或明确恢复时设置，不在每帧、每次 React 渲染或每次详情路由变化时重置。
- 优先使用 React 内置状态和派生数据；确实需要时再评估额外状态管理库。
- 搜索与分类结果通过同一数据源派生，场景和列表不得各自维护一套过滤逻辑。
- 详情选中状态与路由协调更新，避免路由、场景和列表各存一份可能冲突的选中值。
- 不在每一帧渲染中触发 React 全局状态更新。

## 5. 3D 场景与资源实现

### 5.1 空间与锚点

- 按[3D 场景描述](./04-scene-description.md)实现店外入口、关闭店门、前台、服务员、主货架和可行走边界。
- `spawn.new`、`spawn.returning`、`door.entry`、`npc.attendant`、`interaction.counter`、`shelf.main` 等锚点集中配置并具有稳定语义。
- 先用简单灰盒验证尺度、出生点、入口至前台路线和碰撞，再替换为 AI 生成或制作的最终资源；不能先做精美模型后发现无法行走。
- 场景资源不能决定用户身份或注册结果，只负责提供锚点、交互目标和空间表现。
- 游戏盒和货架由通用陈列逻辑生成，不能硬编码单款游戏的位置、模型或镜头。

### 5.2 几何、模型与纹理

- 优先使用可复用的程序化几何体构建店铺和灰盒，避免为简单物件引入大型模型包。
- 共享几何体和材质；重复物件较多时使用实例化。
- 游戏封面使用本地优化资源并控制纹理尺寸，避免把原图直接作为大尺寸纹理加载。
- 确需模型时使用本地压缩 glTF/GLB，并控制首屏加载体积。AI 生成结果必须经过结构、命名、法线、轴心、尺度、碰撞和性能检查，不能直接导入后视为完成。
- AI 生成或辅助生成的资源应记录来源、生成方式和许可检查结果，不使用侵权角色、品牌或来源不明的纹理。
- 店门必须保留独立门扇和正确门轴；服务员、货架和需要单独控制的物体不能全部合并成不可编辑的单一网格。
- 移动碰撞代理与渲染模型分离，优先采用简单稳定的碰撞形状。游戏盒交互射线与移动碰撞分开处理。
- 3D 场景按需加载，首屏先提供可操作的基础界面和加载状态。
- 只对可交互物件进行必要的射线检测，不将大量装饰纳入交互检测。

## 6. 自主移动、店门与接待实现

### 6.1 桌面移动与视角

- 实现桌面端用户自主移动，不再以固定机位切换代替店内行走。
- 第一/第三人称、移动按键、鼠标灵敏度和指针锁定方案确认后再锁定实现；未确认前不得声称多种视角均已支持。
- 移动输入、视角输入和页面控件输入应有明确焦点边界。用户能够使用 `Escape` 释放画布输入，并通过 `Tab` 到达注册、搜索、详情和模式切换控件。
- 移动和动画基于帧间隔计算并限制异常大的时间步长，避免切换标签页后瞬移或穿过碰撞。
- 对墙体、地面、店门、柜台、服务员、中心雕塑和主货架实施必要碰撞与边界约束，出生点和柜台交互点必须先验证不与碰撞体重叠。
- 提供卡住恢复或安全位置重置。恢复不得修改注册状态、筛选条件、显示模式或选中游戏。
- 当前不实现手机触摸移动，也不把 WASD 等具体按键支持表述为手机端能力。

### 6.2 店门状态机

- 店门至少区分 `closed`、`opening`、`open`、`closing`，动画状态、交互状态和碰撞状态由同一状态机协调。
- 场景初始不得默认敞开门。新用户从店外关闭门前开始；已注册用户虽出生在店内，也不能因此把店门默认设为打开。
- 开关动画围绕真实门轴执行，不移动用户或强制转动用户相机。
- 明确定义重复交互、动画中交互和减少动态效果的行为，避免多次点击造成动画叠加、状态反转错误或碰撞与画面不一致。
- 关闭门不能直接被穿过；打开后的通道不能仍被不可见碰撞体封住。
- 店门动画是功能性动画，不套用普通 UI 反馈的 300ms 上限，但必须可测试并避免长时间阻塞入口。

### 6.3 服务员接待与注册

- 新用户通过自主移动到达柜台交互区域后，主动触发服务员和注册对话；不得自动传送到柜台。
- 已注册用户从 `spawn.returning` 开始，并面向 `npc.attendant` 触发一次简短问候，不执行店外入店流程。
- 同一次页面访问中，场景恢复、模式切换和详情导航不得重复触发已完成的问候或注册。
- 注册表单使用语义化 DOM 控件实现，场景只提供接待上下文；关键文字、输入和错误信息不能只存在于纹理或画布中。
- 对话或表单打开时，暂停与其冲突的移动输入，关闭后恢复移动与焦点；不能因释放指针锁而意外重复提交表单。
- 注册成功后保留柜台区域的位置并恢复移动，不重新加载页面或重置到 `spawn.new`。

## 7. 性能与故障隔离

- 限制桌面设备像素比，并根据实际桌面性能预算控制渲染质量；不再以移动端降级规则代替桌面验收。
- 控制动态阴影、动态光源、透明材质和后处理数量，不依赖高成本实时反射或重型后期效果营造氛围。
- 避免在每帧循环中创建新对象、纹理、材质和数组。
- 用户静止且无动画时停止不必要的连续渲染；移动、门动画或必要反馈期间恢复渲染。
- 页面不可见时暂停非必要动画、渲染和音频，并在恢复时避免累积过大的帧间隔。
- 模型、纹理和音频按需加载，不一次下载全部后续资源。
- 隔离场景、封面和音频的资源错误；关键 3D 资源失败时保留必要的注册、列表、详情和启动能力。
- WebGL 不可用、3D 初始化失败或关键场景资源失败时，提供等价的 DOM 注册入口和桌面列表，不要求用户修复画布后才能继续。
- 正常运行不得出现持续警告、重复报错或资源 404。

## 8. 可访问性实现

- 3D 游戏选择必须提供对应的 DOM 操作入口，画布不能成为唯一选择方式。
- 使用语义化按钮、链接、表单标签和必要的无障碍名称；不可仅用 `div` 模拟交互控件。
- 实现可见焦点、模态弹层焦点约束和关闭后的焦点恢复。
- 画布移动输入不得劫持注册表单中的键盘输入，也不得使 `Tab` 和 `Escape` 无法使用。
- 桌面布局需要覆盖 200% 缩放、文字换行和主要操作可见性；当前不要求小屏和移动端布局测试。
- 减少动态效果模式应同时作用于 3D 视角、游戏盒、店门和界面切换动画。店门可以简化，但其开关状态必须可辨认。
- 所有状态不能只靠颜色表达，普通文本、表单错误和按钮状态应提供可读文字。

## 9. 测试与验证

添加与当前规模匹配的基础测试，至少覆盖：

- 游戏搜索与分类组合筛选。
- 空结果与清除筛选。
- 根据 `slug` 找到或拒绝游戏。
- 可用、维护中、未开放及启动地址缺失或无效时的按钮状态。
- 场景与列表共享选中状态的核心逻辑。
- 筛选排除当前选中游戏后的清理行为。
- 缺少封面时使用默认封面。
- 新用户与已注册用户到不同出生锚点的映射，以及身份加载或错误时不误用已注册状态。
- 店门初始关闭、开关状态转换、重复交互和碰撞状态协调。
- 新用户柜台注册、注册失败、注册成功后保持位置，以及已注册用户问候不重复执行。
- 移动边界、安全位置恢复和浏览状态不被重置的核心逻辑。
- WebGL 失败后的 DOM 注册、列表浏览、详情和有效游戏启动。
- 主要浏览、选择、详情和启动流程的集成测试。
- 外链协议校验及不存在游戏的启动拦截。

完成后执行项目定义的测试和生产构建，修复实际出现的错误。环境支持桌面浏览器测试时，检查首页加载、新用户门外出生与开门入店、已注册用户柜台出生与问候、自主移动与碰撞、注册成功和失败、游戏选择、列表切换、搜索、详情 URL 刷新与前进后退、200% 缩放、键盘与焦点、指针释放、减少动态效果，以及 WebGL 降级流程。手机端和触摸移动不属于当前验证范围。

## 10. 实施顺序

1. 检查目录和现有工程，确定最小技术方案，并确认身份接口、视角和控制方案中的已决与待决项。
2. 建立应用、路由、游戏数据、身份状态边界和基础样式。
3. 先完成列表、搜索、筛选、详情与启动流程。
4. 按场景描述建立灰盒、逻辑锚点、可行走边界和两种出生点。
5. 完成桌面自主移动、碰撞、安全恢复和店门状态机，验证门外至柜台路线。
6. 接入服务员接待、新用户注册和已注册用户问候；正式接口未决时使用明确隔离且标识清楚的开发实现，不冒充正式服务。
7. 制作或生成 AI 场景资源，完成版权、结构、尺度、门轴、碰撞和性能检查后替换灰盒。
8. 创建通用货架与游戏盒，连接场景、列表、详情、筛选与 URL 状态。
9. 完成桌面键盘、焦点、减少动态效果、WebGL 降级和资源异常处理。
10. 优化加载、渲染和资源体积。
11. 执行测试、生产构建和可执行的桌面浏览器验证，修复问题后再交付。

## 11. 技术验收与交付说明

- 项目可以安装依赖并正常启动、测试和构建。
- 首页展示真实可交互、可自主移动的 3D 店铺，不以静态背景图、概念图或视频代替。
- 新用户与已注册用户分别从场景规定的门外和柜台前锚点开始，身份未确认或失败时不会误用已注册流程。
- 店门初始不敞开，开关动画、门轴、碰撞和重复交互行为正确；新用户无需强制镜头动画即可自主入店。
- 已注册用户问候、新用户注册及注册成功后的状态与位置保持符合产品要求；模拟能力没有被描述为正式账号服务。
- 新增游戏不需要修改场景组件，AI 场景资源具有可编辑结构、稳定锚点和必要碰撞。
- 主要流程集成测试、身份与出生点测试、门状态测试、数据筛选测试和异常状态测试通过。
- 不存在持续控制台错误、重复警告、资源 404 或可触发空白页的启动入口。
- 交付时简要说明已实现功能、启动与构建命令、实际测试结果，以及仍需接入的真实身份服务、游戏数据或场景资源；未执行的桌面浏览器验证必须明确说明，不宣称手机端或后续独立 2D 网站已经完成。
