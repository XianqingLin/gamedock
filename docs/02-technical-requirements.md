# GameDock：技术实现要求

本文规定工程、数据、部署、安全和测试要求。用户可见行为与默认规则以[产品需求](./01-product-requirements.md)为准，进度与决策追溯见[开发日志](./devlog.md)，本文不重复定义业务规则。

## 1. 交付方式与技术栈

直接在当前工作目录交付可运行的实际代码、本地资源和必要配置，而不是示例、设计稿或代码片段。若已有工程，先检查并沿用现有技术栈与结构：

- 前端：Vite + React + TypeScript + React Router，结构清晰的普通 CSS；测试用 Vitest 与 React Testing Library。
- 平台后端：Cloudflare Workers（`server/worker.mjs` + `wrangler.jsonc`），业务模块面向存储接口编程。
- 存储：D1（用户/好友）、KV（玩家存档）、R2（游戏静态资源，bucket `gamedock-games`）。
- 本地开发：`wrangler dev`（本地模拟 D1/KV/R2）+ vite 代理；测试向业务模块注入内存/fs 实现。

不为简单功能提前搭建无关后端，不引入只解决假想需求的大型依赖，也不增加无实际作用的抽象层、通用框架或复杂事件总线。

## 2. 域名与部署形态

- 主域 `gamedock.cn` / `www.gamedock.cn`：Static Assets 托管 SPA；`/api/*` 业务 API；`/g/*` 生产环境 301 到内容域。
- 内容域 `games.gamedock.cn`：R2 托管游戏静态资源，key 为 `g/<slug>/<路径>`，与 URL 路径一一对应；目录路径回退 `index.html`；游戏与平台跨源隔离。
- 会话 Cookie 为 host-only + SameSite=Lax：不进入游戏域；`/api` 的 CORS 仅放行内容域与请求自身源（带凭据），不对第三方源开放。
- 平台发布 = `npm run deploy`；游戏发布 = `node scripts/sync-games.mjs`（`--local` 喂本地模拟）。平台构建不接触游戏产物。
- 发布一致性：R2 无原子目录替换，sync 脚本先传普通文件、最后写各游戏 `index.html`。
- 本地 dev 注意：`wrangler dev` 配置自定义域后会把请求 URL 的 host 重写为第一个自定义域，生产判定不能依赖 hostname（以 https 协议为准）；游戏域分支的行为以单测覆盖。

## 3. 路由与启动实现

- `/`：首页，承载游戏库浏览。
- `/games/:slug`：游戏详情，支持直接访问、刷新恢复、浏览器前进和后退。
- `/play/:slug`：游戏运行页（外边框 + 跨源 iframe）。
- 其他路由：显示路由未找到状态和返回首页入口。

关闭详情与筛选导致选中失效时，应同步清理对应详情路由，避免 URL 继续指向已取消选择的游戏。

启动处理要求：

- 站内游戏在跨源 iframe 中加载，iframe src 指向内容域完整地址；本地 dev 经代理保持同源路径。
- 外链只接受 `http:` 和 `https:` 协议；解析后协议不符合要求时按无效地址处理，不执行 `javascript:`、`data:` 等地址。
- 使用新窗口打开外链时设置 `noopener`、`noreferrer` 等安全属性。
- 游戏不存在、未开放、维护中或启动地址缺失、无效时，不创建空白路由或空白窗口。
- 启动失败不能破坏当前浏览状态。

平台 ↔ 游戏 postMessage 接口要求：

- 信封带协议版本号，平台消息 `platform:` 前缀、游戏消息 `game:` 前缀。
- 平台校验 `event.source` 与 `event.origin`（预期为 iframe 自身源），游戏侧同样校验来源。
- 握手时序双方兜底：平台加载完成后先发 hello，游戏就绪后可请求重发，谁先就绪都能完成握手。
- 登录态未确认前不挂 iframe；登录态在加载后才就绪时重发 hello 补发最终用户。

## 4. 游戏数据

游戏库、列表和详情必须使用同一份数据（`src/data/games.json`），参考结构如下，可按实际需要最小调整：

```ts
type GameStatus = 'available' | 'coming-soon' | 'maintenance'

interface Game {
  id: string
  slug: string
  title: string
  cover: string
  accentColor: string
  categories: string[]
  description?: string
  launchUrl?: string
  status: GameStatus
  version?: string
  order: number
}
```

数据约束：

- `id` 和 `slug` 必须唯一且稳定，不以数组下标充当持久标识。
- 默认按 `order` 升序排列；`order` 相同时按 `id` 排序，保证结果稳定。
- 可选字段没有有效数据时保持缺省，不渲染空标签。
- 第一款游戏与其他数据使用相同结构和组件。
- 演示数据只能用于开发、测试或明确的演示环境，不得伪装为正式接入内容。
- 新增游戏 = `server/games.config.json` 声明产物目录 + games.json 加数据；不改平台代码。
- 存档等接口的 slug 校验与游戏数据保持一致（未接入 slug 返回明确错误）。
- 封面路径无效或资源加载失败时统一回退到本地默认封面，不使用随机外链占位图。

## 5. 用户、组件与状态管理

### 5.1 身份与会话

- 注册/登录/登出/当前用户接口按真实方案实现，不伪造注册能力。
- 密码使用 PBKDF2-SHA256 加盐哈希存储，不保存或传输明文密码；敏感凭据不写入本地存储、日志或游戏数据。
- 会话为无状态签名 Cookie（HMAC-SHA256，httpOnly + SameSite=Lax，host-only，生产 Secure）；密钥经 secret 注入，不入库。
- 至少区分身份加载、未登录、已登录和身份错误状态；身份未确认时不默认按已登录处理。
- 会话过期或签名非法时按未登录处理，不误用旧身份。
- 存储接口双实现：内存/fs 实现供测试，D1/KV 实现供线上；业务代码只面向接口。

### 5.2 组件与状态拆分

- 按职责拆分页面、卡片、详情、搜索筛选、账号区、好友面板、运行页外边框与游戏帧，避免为单款游戏写特殊分支。
- 优先使用 React 内置状态和派生数据；确实需要时再评估额外状态管理库。
- 搜索与分类结果通过同一数据源派生，不得各自维护一套过滤逻辑。
- 选中状态与路由协调更新，避免路由与界面各存一份可能冲突的选中值。

## 6. 性能与故障隔离

- 静态资源带明确缓存策略：index.html 不缓存，普通资源短缓存。
- 按需加载，不一次下载全部后续资源。
- 隔离封面等资源错误；单个资源失败不导致整个应用不可用。
- 正常运行不得出现持续警告、重复报错或资源 404。

## 7. 可访问性实现

- 使用语义化按钮、链接、表单标签和必要的无障碍名称；不可仅用 `div` 模拟交互控件。
- 实现可见焦点、模态弹层焦点约束和关闭后的焦点恢复。
- 桌面布局需要覆盖 200% 缩放、文字换行和主要操作可见性；当前不要求小屏和移动端布局测试。
- 所有状态不能只靠颜色表达，普通文本、表单错误和按钮状态应提供可读文字。

## 8. 测试与验证

添加与当前规模匹配的基础测试，至少覆盖：

- 游戏搜索与分类组合筛选；空结果与清除筛选。
- 根据 `slug` 找到或拒绝游戏。
- 可用、维护中、未开放及启动地址缺失或无效时的按钮状态；外链协议校验及危险协议拦截。
- 筛选排除当前选中游戏后的清理行为。
- 缺少封面时使用默认封面。
- 注册/登录/登出/当前用户全流程，含错误密码、重复注册拒绝与会话伪造拒绝。
- 好友请求全流程（发送/接受/拒绝/取消/删除）及无效操作的拒绝。
- 存档写读列删、slug 校验、大小上限与未登录拒绝。
- CORS：内容域放行（含 preflight）、自身源放行、第三方源拒绝。
- R2 静态资源服务：目录回退、Content-Type 推断、缓存策略、Range 请求、路径穿越拒绝、未命中 404。
- Worker 路由分流：游戏域、主域重定向、本地 dev 直读、SPA 回退。
- 主要浏览、选择、详情和启动流程的集成测试。

完成后执行项目定义的测试、类型检查和生产构建，修复实际出现的错误。环境支持桌面浏览器测试时，检查首页加载、注册登录、游戏浏览与启动、详情 URL 刷新与前进后退、200% 缩放、键盘与焦点。手机端和触摸操作不属于当前验证范围。

## 9. 实施顺序

1. 建立应用、路由、游戏数据与基础样式。
2. 完成列表、搜索、筛选、详情与启动流程。
3. 实现账号体系（注册/登录/会话）与个人主页。
4. 实现好友关系与平台存档接口。
5. 接入部署形态：Workers + D1/KV + 自定义域；游戏静态资源迁 R2 并拆分内容域。
6. 实现游戏运行页（外边框 + 跨源 iframe + postMessage 握手）。
7. 补齐可访问性、异常降级与安全校验。
8. 执行测试、生产构建与线上验证，修复问题后交付。

## 10. 技术验收与交付说明

- 项目可以安装依赖并正常启动、测试和构建；`npm run deploy` 可重复部署。
- 主域承载 SPA 与 API；游戏域承载游戏静态资源且与平台跨源隔离；`/g/*` 在主域生产环境重定向。
- 游戏发布不触碰平台仓库；平台构建产物不含游戏文件。
- 存储层可替换（内存/fs ↔ D1/KV/R2），测试不依赖真实云资源。
- 全部测试、类型检查和生产构建通过；不存在持续控制台错误、重复警告、资源 404 或可触发空白页的启动入口。
- 交付时简要说明已实现功能、启动与构建命令、实际测试结果，以及仍需接入的真实服务（如好友邀请、联机身份凭证）；未执行的验证必须明确说明。
